> 日期：2026-11-23 · 状态：**待审查（未执行任何写入/安装/定时任务）**
> 目标：为 `@honorshine/dsh-desktop-notify` 建立「自动采集 → 落库 → 静态看板」的下载量统计，覆盖 npm 与插件市场两个口径、日/周/月/年四级周期。

## 0. 结论先行

1. **可以全自动、零新增依赖**：Node 26 自带 `node:sqlite` 与 `fetch`，不需要 pnpm 装包、不需要 Python。
2. **但"两个数据源"有一个硬事实需要你拍板**：市场上展示的「下载量（近 30 天）」**就是 npm 下载量**，市场没有独立的安装计数。当前市场页显示：`Star 1`、`下载量（近 30 天）1,175`、`收录于 2026-11-08`。详见 §2。
3. 因此本方案默认把两张图定义为**同源不同口径**：图 A = npm 日增量，图 B = 市场口径的近 30 天滚动值。二者曲线形态不同，不是重复图。若你有市场后台的真实安装数据，方案预留 adapter 替换（D1-B）。
4. 需你在审查时拍板 4 项：**D1 市场口径 / D2 自动化方式 / D3 落盘位置 / D4 是否公网发布**。

## 4. 方案设计

### 4.1 总体架构

```
npm registry ─┐
npm downloads ─┼─→ collect.mjs ─→ stats.db (SQLite) ─→ build.mjs ─→ site/data.js + index.html
market page ──┘        (幂等 upsert)      (日表 + 元数据)      (聚合四级)     (静态，file:// 可开)
                                     ↑
                              run.cmd ← 任务计划（每日 09:10）
```

- **采集与展示解耦**：页面不联网，只读 `data.js`；采集失败不影响已生成页面。
- **单一事实来源**：DB 存"逐日原始值"，四级周期全部在构建时派生，不重复存储。

### 4.2 目录结构

```
stats/
├─ collect.mjs        # 取 npm 元数据 + 逐日下载量 + 市场校验，写 DB
├─ build.mjs          # DB → 四级聚合 → 写 site/data.js
├─ db.mjs             # 建库/迁移/连接
├─ lib/aggregate.mjs  # 周期聚合（纯函数，可单测）
├─ test/aggregate.test.mjs
├─ run.cmd            # collect + build 一条命令
├─ register-task.ps1  # 注册/卸载计划任务（展示命令，不自动执行）
├─ data/stats.db      # gitignore
└─ site/
   ├─ index.html      # 两个图表卡片
   ├─ app.js / style.css
   └─ data.js         # 生成物，gitignore
```

### 4.3 数据库结构

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);            -- first_publish, latest_version, market_listed_at, ...
CREATE TABLE daily (day TEXT PRIMARY KEY,                          -- UTC 'YYYY-MM-DD'
                    downloads INTEGER NOT NULL,                   -- npm 日增量
                    fetched_at TEXT NOT NULL);
CREATE TABLE market (day TEXT PRIMARY KEY,                        -- 抓取日
                     downloads_30d INTEGER,                       -- 市场展示值（校验用，可空）
                     stars INTEGER, listed_at TEXT, fetched_at TEXT);
CREATE TABLE runs (id INTEGER PRIMARY KEY, started_at TEXT, ok INTEGER, detail TEXT);
```

`daily.day` 主键 + `INSERT ... ON CONFLICT(day) DO UPDATE` 保证**重复采集幂等**。

### 4.4 采集策略

1. 读 `meta`（没有则从 registry 拉一次）→ 得到 `first_publish`。
2. 回看窗口 = `max(first_publish, 今天 - N 天)`，N 默认 7（覆盖 npm 约 1 天延迟 + 断档补数）；`--backfill` 参数可一次拉全量。
3. `GET /downloads/range/{start}:{today}/{pkg}` → 逐日 upsert。
4. 可选：抓市场插件页，正则提取 `下载量（近 30 天）` / `Star 数` / `收录于`，与本地滚动和对比；差异 > 5% 记 `runs.detail` 告警，**不写覆盖**。
5. 失败处理：网络错误重试 3 次（指数退避）；仍失败则记 `runs(ok=0)` 并以退出码 1 结束，**DB 与既有页面保持原状**。
6. 时区：npm 按 UTC 日统计，DB 一率存 UTC；页面标注 `UTC`，可加"本地日"偏移开关（默认关）。

### 4.5 聚合规则（四级周期）

| 周期 | 分桶 | 默认展示窗口 | 主数字 |
|---|---|---|---|
| 每天 | 自然日 | 最近 30 天 | 窗口内合计（等价于图一的周/月卡片） |
| 每周 | ISO 周（周一起） | 最近 12 周 | 当周合计 |
| 每月 | 自然月 | 最近 12 月 | 当月合计 |
| 每年 | 自然年 | 全部 | 当年合计 |

- 图 A：各桶**增量合计**。
- 图 B（D1-A）：各桶取**桶末的 30 天滚动值**（日=当天值，周=周日值…），语义在页面上明写，避免误读。
- 首日之前的桶不补 0、不画线（避免"发布前就有下载"的假象）。

### 4.6 页面设计（还原图一）

单页、两列（窄屏堆叠），每张卡片：

```
┌────────────────────────────────────────────┐
│  ↓  2026-11-16 to 2026-11-22        [日|周|月|年] │
│  1,103                                     │
│  ╭──────────────────────────────────╮─●   │   ← 折线 + 渐变面积 + 末端点
│  ╰──────────────────────────────────╯     │
└────────────────────────────────────────────┘
```

- 视觉对齐参考图：紫色主线（`#8b5cf6` 系）、浅紫面积填充、末端实心点、左上"下载"图标 + 区间文案、下方大号数字（千分位）。
- 交互：hover 显示该点日期与数值；周期切换为顶部 tab，两卡共用（也可独立，见 D2 备注）。
- 无网络依赖：字体用系统栈，图表 SVG 由 `app.js` 现场生成。
- 空数据/单点数据要能正常渲染（不给假数据）。

### 4.7 自动化

`stats/run.cmd`：

```bat
@echo off
cd /d %~dp0
node collect.mjs --backfill-if-empty
node build.mjs
```

`register-task.ps1` 仅**打印**并需你确认后执行：

```powershell
schtasks /create /tn "dsh-desktop-notify-stats" /tr "D:\...\stats\run.cmd" /sc daily /st 09:10 /f
```

（`/f` 覆盖同名任务；不使用管理员权限，与当前用户绑定。）

### 10.2 市场数字的实测结论

市场页「下载量（近 30 天）」= npm 30 天滚动值，但滞后 1 天：
2026-11-23 抓取页面显示 `1,175`，等于本地滚动截至 2026-11-20 的值（窗口 10-22～11-20）。
`build.mjs` 会在最近 4 天里寻找匹配项，命中即视为校验通过，并在页面脚注标注滞后天数；不匹配才告警。

### 10.3 与计划的偏差

- 采集不再"回看 7 天"，改为每次从首版日期全量重取（16 天数据，幂等 upsert，成本可忽略，且天然补齐缺口）。
- 周期聚合只有 1 个桶时（如刚发布的月份）向前补空周期到 3 个，否则页面只剩一个孤点。
- 受限沙箱内 Node 无法 `spawn` git（EPERM），`publish.mjs --branch` 会自动生成 `dist/publish-branch.sh` 供普通终端执行。

### 10.4 口径调整（用户反馈）

初版 npm 卡片大数字为「当期值」（与 npm 官方页一致）。用户反馈需要总下载量，故改为：

- 顶行区间 = 整体覆盖区间（2026-11-08 to 2026-11-21），与累计口径对应；
- 大数字 = `totals.npmAll`（自首版以来累计）；
- 副行 = 当期值（`本周 1,103`、`当日 395` 等），随 tab 切换；
- 市场卡片不变（近 30 天滚动本就是窗口值），副行隐藏。

`build.mjs` 早已输出 `totals.npmAll`，本次只改前端 `app.js`/`index.html`/`style.css`，定时任务无需改动。

### 10.5 市场累计口径（追加需求）

用户提出：市场页只展示「近 30 天」，能否据此还原「自发布以来累计」，并用当日值减前一日值得到当日下载量。

结论与实现：

- **当日值不能直接由两个滚动值相减得到**。设 M(t) 为 t 日的 30 天滚动值，则
  `M(t) - M(t-1) = d(t) - d(t-30)`：只有当 t 距今不足 30 天（窗口还没越过首版日）时才等于 d(t)；一旦窗口开始滑出旧数据，差值就变成「净变化」，会少掉 30 天前那天的下载量。
- **但累计量可以还原**：`累计(t) = M(t) + Σ(d(i) for i < 窗口起点)`。窗口起点 = t-29；已滑出的天数直接从 npm 逐日表补回来（npm 才是权威数据源）。
- 本包 2026-11-08 发布，当前第 16 天，窗口起点 2026-10-25 早于首版 → 市场页的 1,175 本身就是累计（对应截至 11-20 的窗口，滞后 1 天）。
- `build.mjs` 输出 `market.cumulative = { asOf, raw30d, windowStart, windowCoversPublish, droppedOut, total }`；页面市场卡片大数字改为该累计值，副行保留「近 30 天」原值并注明当前处于哪种情形。
- 市场页每天只吐一个滚动数字，本身不提供额外信息（它就是 npm 的滚动值）。每期快照都存在 `market` 表里，可用于观察滞后与页面改版，但**不能**独立还原历史逐日下载量——历史逐日只能来自 npm。

### 10.6 市场折线截止到自身统计日

用户反馈「两张图曲线和数据几乎一样」。核查结论：不是 bug——市场页的数字本来就是 npm 的 30 天滚动值（同源），且当前发布不足 30 天，滚动值 = 累计值，所以两条线都在跟着累计增长。但确实存在一处真实的矛盾：

- 市场卡片大数字取市场页实际展示值（1,175，对应统计日 11-20），
- 而市场折线取本地滚动值，末端到 11-21（1,570），
- 于是「曲线末端」与「卡片数字」互相打架。

修法：`build.mjs` 先做市场页校验拿到市场统计日（`match.day`），再把它之后的滚动点截掉，折线止于 1,175；月/年视图的市场桶也随之变成 1,175，与卡片一致。npm 卡片不受影响，仍到 11-21。

### 10.7 收敛为单一 npm 数据源

用户指出：市场页的下载量就是按 npm 数据统计的，两张卡片重复。确认属实——市场页展示值只在 [10-25, 11-23] 窗口上与本地 npm 滚动值完全相等（1175 = 截至 11-20 的滚动值），没有独立安装计数。

改动：

- 页面只保留一张 npm 卡片（单列居中，最大宽度 640px），去掉市场卡片及其折线；
- `build.mjs` 不再计算市场滚动序列、市场累计、市场校验，`stats.series.market`、`stats.totals.market30d`、`stats.market.cumulative/check` 全部移除；
